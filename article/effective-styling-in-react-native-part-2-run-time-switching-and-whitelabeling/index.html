Effective Styling in React Native, part 2: Run-time switching & whitelabeling

by
Mitchell Coutinho

Welcome to part two of my series on styling in React Native. In the first part, you’ve learned some basics regarding React Native architecture.

#JavaScript

You’ve also learned how to leverage that knowledge to set your project up to be maintainable, to prevent compile-time bugs using TypeScript, and to prevent mental overhead and run-time bugs by avoiding error-prone Flexbox properties. 

In this second part, we’re going to expand on that knowledge and look at powerful strategies to switch between styles at both compile-time and run-time. We’ll also look at how to document your components and all of their variants.

Run-time switching

Our strategy so far combines a good developer experience with maintainability. But what if we wanted to give the user the choice to choose between styles at runtime? To switch, for instance, between light-mode and dark-mode, or different themes?

There are libraries that support this kind of functionality, but they tend to have a significant impact on your software architecture. I don’t want to make any assumptions about the libraries you are using. Instead, allow me to talk you through a convenient way of implementing this yourself. I’ll be using light-mode and dark-mode as an example.

There are two basic truths that we have to deal with when we try to offer run-time style switching. The first is that we need to prepare two different sets of styles. The second is that we’re forced to verify at run-time which style choices the user has made before applying the right style in components. That means executing code and using branching statements. Luckily for us, React can handle the execution part. After all, React components are simply functions that are called by the framework when necessary.

But what about the branching statements? We don’t want to have to use extra branching statements in every component that uses styles, since that would add a lot of clutter and maintenance overhead. Not to mention, it would force us to handle those branches in unit tests if we were aiming for a certain amount of test coverage. If you ask me, there is no reason developers implementing components need to be made constantly aware there that there are different versions of the styles they apply. Instead, let’s aim for maximum developer convenience!

Before we go through the implementation details that make the magic happen, let’s look at our future Title component to see what experience you’ll get when you use this approach. First, we change Title.style.ts as follows:

// Title.style.ts

import {StyleSheet} from '../../utilities/customStyleSheet';
import {basicTextMixin} from '<mixins folder>/text.ts';

const light = {
 titleText: {
   ...basicTextMixin,
   backgroundColor: '#BBBBBB',
 },
};

const dark = {
 titleText: {
   ...basicTextMixin,
   backgroundColor: '#333333',
 },
};

export default StyleSheet.create(light, dark);

The first change is obvious. We write two styles instead of one. The second is subtle. Instead of using the original StyleSheet.create() function, we now use a custom version of StyleSheet.create() that accepts two style objects instead of one. Feel free to refactor your style objects as you see fit. You could for instance find ways to reduce duplication or split the light and dark styles to their own respective files.

Meanwhile, the Title.tsx component implementation changes as follows:

import {FunctionComponent} from 'react';
import {Text, View} from 'react-native';
import style from './Title.style';

interface Props {
 text: string;
}

const Title: FunctionComponent<Props> = ({text}) => {
 return (
   <View>
     <Text style={style.titleText}>{text}</Text>
     </View>
 );
};

export default Title;

If you’re having trouble spotting any differences, that’s because there are none! From the developer’s perspective, nothing has changed at all!

And yet, when the user changes their Native theme settings, the styles in the app will change along to accommodate them. So how do we achieve this kind of magic? Let’s see how the run-time switching works.

First, you should know that React Native exposes a hook to keep track of the user’s chosen native color scheme, so I use that in my implementation. If you’re switching between different kinds of themes, feel free to swap the following code out for something more appropriate to your needs. As long as you can manipulate a variable to stores the user’s choice, you’re all good.

To enhance the developer experience, we’re trying to keep our components in the dark about the existence of multiple themes. But at the same time, I’m relying on a hook in this example. Since hooks can only be called from custom components or custom hooks, and since we don’t want to burden the components, that leaves us with the option of making our own custom hook:

// useChosenTheme.ts

import {useColorScheme} from 'react-native';

let chosenTheme = 'light' as unknown as ReturnType<typeof useColorScheme>;

const useChosenTheme = () => {
 chosenTheme = useColorScheme();

 return chosenTheme;
};

export {chosenTheme, useChosenTheme};

Here, we make a new module useChosenTheme.ts to write our hook useChosenTheme in. The hook calls useColorScheme, a hook exposed by React Native to check the user’s native color scheme preference. It saves the result to a the variable chosenTheme every time it is run. Meanwhile, the module exposes that variable with an export. Code that imports chosenTheme from this module will be able to see the latest chosen value whenever it evaluates the variable. You may know this approach as the module pattern.

Next, we make a new component called WithTheme that accepts children and passes them along. It uses our custom hook and saves the results of running the hook to local state. The state is passed to children as a prop. Lastly, it listens for changes to this state with useEffect:

// WithTheme.tsx
import {Children, ReactElement, useEffect, useState} from 'react';
import {useChosenTheme} from '../../utilities/useChosenTheme';

type Theme = ReturnType<typeof useChosenTheme>;

interface Props {
 children: ReactElement;
}

export const WithTheme = ({children}: Props) => {
 const chosenTheme: Theme = useChosenTheme();

 const  = useState<Theme>('light');

 useEffect(() => {
   if (chosenTheme !== currentTheme) {
     setCurrentTheme(chosenTheme);
   }
 }, );

 return Children.map(children, (child, index) => {
   return (
     <child.type key={index} chosenTheme={chosenTheme} {...child.props} />
 );
 });
};

Note that you don’t have to worry about using index as a key here, since we’re wrapping the app’s top-level components

In App.tsx, we wrap our entire app’s component tree in <WithTheme/>.

// App.tsx

import Title from './src/components/Title/Title';
import WithTheme from './src/components/WithTheme/WithTheme';

const App = () => {
 return (
   <WithTheme>
     <Title text={'Hello World'} />
 </WithTheme>
);
};

export default App;

With this setup, WithTheme relies on our useChosenTheme() hook, which in turn relies on React Native’s useColorScheme() hook. Whenever a user changes their system’s light/dark mode preference, WithTheme, useChosenTheme() and useColorScheme() are called in order. In WithTheme, this triggers the newly chosen theme to be stored to the variable chosenTheme, and useEffect will notice this change and call setCurrentTheme().

The reason we want to update currentTheme is that updating WithTheme’s internal state causes it to re-render, in turn causing all the children to re-render. This trickle-down effect through the entire app is necessary because all components need to re-apply their styles to match the user’s new choice. (Note that if you have any memoized components, you may have to trigger them to re-render separately using an approach that makes sense for your project.)

Lastly, let’s see what other magic goes on under the hood of our custom StyleSheet object to make this possible.

// customStylesheet.ts
import {chosenTheme} from './useChosenTheme';
import {StyleSheet as OriginalStyleSheet} from 'react-native';

interface CustomStyleSheet {
 create: <T extends StyleObject>(light: T, dark: T) => T;
}

interface StyleObject {
 [key: string]: any;
}

export const StyleSheet: CustomStyleSheet = {
 create: (light, dark) => {
   const styleSheet = {} as StyleObject;
   recursivelyReplaceFields(styleSheet, light, dark);
   return styleSheet as typeof light;
 },
};

/**
* Find the most deeply nested objects and replace them with getters
* that dynamically find the right styles to return
*/
const recursivelyReplaceFields = <U extends T, T extends StyleObject>(
 resultingStylesheet: T,
 light: U,
 dark: U,
) => {
 for (const key in light) {
   const currentValue = chosenTheme === 'dark' ? dark[key] : light[key];
   if (isObject(currentValue)) {
     if (hasNestedObject(currentValue)) {
       resultingStylesheet[key] = currentValue;
       recursivelyReplaceFields(resultingStylesheet, light[key], dark[key]);
     } else {
       replaceWithGetter(resultingStylesheet, light, dark, key);
     }
   }
 }
};

const isObject = (styleValue: any): styleValue is object =>
 typeof styleValue === 'object' && styleValue !== null && !Array.isArray(styleValue);

const hasNestedObject = (styleObject: StyleObject): boolean => {
 for (const key in styleObject) {
   if (isObject(styleObject[key])) {
     return true;
   }
 }

 return false;
};

const replaceWithGetter = (
 resultingStylesheet: StyleObject,
 light: StyleObject,
 dark: StyleObject,
 key: keyof StyleObject,
) => {
 const darkValue = OriginalStyleSheet.create(dark[key]);
 const lightValue = OriginalStyleSheet.create(light[key]);

 Object.defineProperty(resultingStylesheet, key, {
   get: function () {
     if (chosenTheme === 'dark') {
       return darkValue;
     } else {
       return lightValue;
     }
   },
 });
};

You can feel free to parse the entire file if you’d like, but I’ll skip over most of the custom type definitions and supporting functions and instead focus on the meat of this module: our exported StyleSheet object. It contains a create function that accepts two style objects: one for each theme we support. We leverage TypeScript’s generic typing to ensure the objects are similar: users can’t accidentally supply a light and dark theme with different properties. If you’re supporting a different number of themes, you can expand this function depending on the number of themes you need to support.

The style objects are then passed on to recursivelyReplaceFields(). This is a relatively simple recursive algorithm that finds the most deeply nested objects inside of our style objects and replaces the properties that reference those nested objects with getters instead. The style objects are passed into the original StyleSheet.create() function, making them immutable and ensuring type compatibility with current and future React Native versions. The getter then forms a closure around each of these style objects. When called, it checks which theme choice the user has made and returns the corresponding object as components get rendered.

The developer is none the wiser. Since this is a getter, its logic is triggered simply by accessing the corresponding property on the object. So when Title.tsx accessed style.titleText, it actually called this logic under the hood.

Note that only the most deeply nested objects get replaced with getters. This ensures that only a single getter is ever involved in the application of a style.

This approach is such a tiny layer of indirection that it should have no performance implications even for large projects with lots of styles applied. If the thought of executing this getter at runtime still worries you, I recommend that you test it with a large number of invocations across a large number of components before deciding whether to optimize. I think you will find that there is no noticeable impact on performance. (If calling a function and running a boolean check during runtime noticeably affects your performance, you probably have other underlying issues in your app that need addressing!)

If you’ve been following along, you now have automated runtime style switching that takes into account performance, introduces no maintenance overhead, makes no concessions to the development experience of your team and only takes up a few lines of code. This all comes on top of all of the benefits our architecture already gives us, and you didn’t need to use a library or change your project structure!

Static switching

It’s awesome to know how to switch between different styles on the fly. But what if you want the opposite? Maybe you’re building a whitelabel app and want to choose the right styles to include in your app during compile time.

There are different ways to solve this problem, but I think that the most elegant one relies on using a babel plugin. Remember that React Native uses Babel to transpile your code, and Metro to bundle it. We’ll leverage these two tools to get the right results.

Imagine that you have the following folder structure:

We’ve made 2 style files and split them up into two different folders. The filenames, however, are identical.

In our component, we import the styles as Title.style, without specifying a path:

// Title.tsx
import {FunctionComponent} from 'react';
import {Text, View} from 'react-native';
import style from 'Title.style';

interface Props {
 text: string;
}

const Title: FunctionComponent<Props> = ({text}) => {
 return (
   <View>
     <Text style={style.titleText}>{text}</Text>
     </View>
 );
};

export default Title;

Next, we manipulate our babel configuration to find the right styles to include during the compilation process.

We start by installing babel-plugin-module-resolver using the command npm i babel-plugin-module-resolver.

We then open our babel.config.js, which at first looks something like this:

// babel.config.js
module.exports = {
 presets: ['module:metro-react-native-babel-preset'],
};

We modify the file as follows:

// babel.config.js
const brandImportPaths = [
 `./src/components/Title/${process.env.BRAND}`,
 `./src/components/Footer/${process.env.BRAND}`,
];

module.exports = {
 presets: ['module:metro-react-native-babel-preset'],
 plugins: [
   [
     require.resolve('babel-plugin-module-resolver'),
     {
       root: [...brandImportPaths, '.', './src'],
       extensions: ['.ts', '.tsx'],
     },
   ]
 ],
};

With these changes, we’ve enabled the custom module resolution plugin. We’ve also added an array of paths and we destructure them into the root array. This array specifies the locations in which the plugin will search when you import modules in your code. In Title.tsx, we no longer specify where we want to import the styles from, so the plugin will actively search for their location using the paths we provide in this configuration. The order of paths in the root array decides the order in which the plugin will search for your imports. This allows us to manipulate the paths where the plugin searches to find the right styles to import in our components.

Also note that the configuration file is a js file. This means the logic inside gets executed before the resulting configuration is applied. We can rely on this aspect of our configuration to specify an environment variable that indicates which brand we want to build for.

To pass an environment variable to the configuration file, you can modify the start command in your package.json file as follows:

// package.json

{
...
 "start": "BRAND=brand1 react-native start --reset-cache",
...
}

This passes the environment variable to react-native’s startup scripts, which in turn starts Babel and Metro. Babel then interprets its configuration, placing your BRAND environment variable in the defined paths in your configuration file. During compilation, when Title.tsx tries to import its styles without a path, Babel will search through its known locations, and the chosen brand’s styles will be found first. This resolves the import, so styles belonging to other brands are effectively ignored during compilation. 

The nice thing about this approach is that we don’t have to worry about cluttering up the resulting app because the ignored styles don’t become bundled with our resulting app at all!

In addition to the environment variable, I have also included the flag--reset-cache in the start command. If you don’t include this flag, Metro will be inclined to keep its cache of previously bundled source files whenever you re-run the start command. This can be confusing because it means that changing the environment variable to a different brand will not result in new styles on your screen. I recommend always resetting the cache during development.

Of course, this is just an example of how you could configure compile-time style switching. You could refactor this approach to create the folder and file structure that you would like to have in your project. Or if you’re working with design tokens that are being imported as npm packages, you could use this setup to point to the right styles in your node_modules folder instead.

Building a whitelabel app is more involved than just updating styling. There is automation involved in dynamically updating names, logos, app IDs, provisioning profiles and more during compile time. You may also want those apps to talk to different back-ends. You can find my contact details below if you’d like advice that is more tailored to your project.

Component Library and documentation

Projects that include a large number of components can benefit greatly from good documentation. This is especially true when you offer your components in different variants or styles.

My favorite tool to document React components is Storybook. It has a lot of features, but most importantly, it allows you to build a component library. This library is a website that contains links to documentation of your components, and your components will render to the webpage as web-based versions of your native components. This embeds actual instances of your React Native components inside of documentation, and comes with inputs such as text fields, check boxes and radio buttons to manipulate the component props and see the results immediately in your browser. 

This is a great way to visualize and interact with your components, as well as share details about them with others. I highly recommend using this tool if you need to document or visualize your components, or if you are looking to build a design system for React or React Native projects.

Adding documentation is simple. Storybook has support for mdx, which is markdown that standard JSX syntax. You can write your documentation in markdown syntax and mix in rendered versions of your component using standard JSX syntax among the text. 

What’s great about using mdx alongside your code to document your component is that it changes along with your code-base. When you remove a prop from a component, you don’t have to go to a separate wiki environment to update the change. Instead, your IDE can help you automatically change the documentation as you change your code. And when you decide you want an older version of your component back, reverting to an earlier git commit will automatically bring back the documentation that matches that version of your component.

 

Storybook can find your documentation if you name the files according to a pattern. If you name and place your files in line with our strategy, your folder structure will look something like this:

When you launch Storybook, it will find your documentation and render it into a website for you. Visit their website to see how. It’s really quite simple.

Once you have it set up, you should probably integrate it into your pipeline to build and deploy the site to an environment of your choosing. Also note that if you are using our white label module resolution strategy, you will need to extend your setup to Storybook. Instead of duplicating your configuration, I recommend that you import your project’s babel configuration into the Storybook babel configuration file, and give the Storybook start command the same environment variable that your project uses in your package.json file.

Conclusion

This concludes my article about styling in React Native. Congratulations on making it to the end! You now know how to effectively style your React Native project!

If you’ve followed along, you’ve learned the following things:

  • how to organize your project.
  • how to prevent runtime bugs while enhancing your development experience. 
  • how to keep your project maintainable as it increases in size
  • how to build multiple variants of your app by compiling the right styles at compile-time. 
  • how to build theme switching functionality that dynamically updates your styles at run-time without any change to the developer experience. 
  • how to document your styles in a way that evolves with your project.
