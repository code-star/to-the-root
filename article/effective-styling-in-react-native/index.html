Effective styling in React Native

by
Mitchell Coutinho

If you’d like to learn an efficient, flexible and maintainable approach to styling your React Native apps, stick around. I’ll share with you all the benefits of my approach, and you’ll pick up enough information along the way to tailor it to your needs.

#JavaScript

If you’re an experienced React Native developer, you already know that the majority of code in React Native projects tends to be spent on building components. You also know that on average, almost all of those components rely on styling. On the Web, React as a framework infamously entices the programmer to interweave that styling with logic and structure, exchanging long-term maintainability for short-term convenience. But unlike on the Web, React Native doesn’t know the concept of CSS classes. It only knows JavaScript and instead only allows you to supply styles in-line to components. This means that the lines between logic and styling are even more blurry, and you as a programmer are being tempted even more to define styles in ways that make your project harder to maintain.

But you don’t have to take the bait. If you’d like to learn an efficient, flexible and maintainable approach to styling your React Native apps, stick around. I’ll share with you all the benefits of my approach, and you’ll pick up enough information along the way to tailor it to your needs.

This is the first article in a two-part series. The first article is divided into three sections. In the first section, you’ll learn the basic aspects of the React Native architecture that directly or indirectly influence how components are styled. In the second section, you’ll learn why those architectural elements influence how you style components. In the last section, I share with you a strategy that’s tailored to helping you build and maintain your apps in a flexible, organized way that prevents runtime bugs. In the second article, I’ll even teach you powerful approaches to switching themes and documenting your styles!

React Native basics

Before we get to strategizing, let’s take a moment to understand the basic building blocks that influence our decisions. React Native is a cross-platform framework. It’s used to build applications that run in multiple environments, most notably Android and i(pad)OS. These operating systems have their own respective methods of dealing with interfaces, yet React Native allows developers to build their app once and deploy it to each of these platforms with a similar UI. It provides this consistency by using a very specific architecture, and there are four parts to this architecture that influence our styling in React Native. In this section, we’re going to look at what these parts are so we can form an effective approach to styling.

First, the React framework itself is used, which means you’ll write your app in JSX. This is essentially syntactic sugar sprinkled atop JavaScript that is well-suited to representing graphical elements and their relationships. But React is of course more than JSX. It provides JavaScript libraries that, among other things, maintain an in-memory Element Tree that represents your layout at run-time. The design of this tree is abstract: functionally, React is about building UIs, but technically, it doesn’t care what this tree will be used for. It can be translated to HTML elements on the web, to the nodes that describe the interfaces in mobile operating systems, to PDF documents or back to code. If you really wanted to, you could even serialize it to plain descriptive text to make an interface just for the visually impaired!

Second, React Native ships with Metro, its very own JavaScript bundler; and Hermes, its very own JavaScript engine. When you write your code as JSX, it gets transpiled to plain JavaScript using Babel and bundled with your app by Metro. The Hermes JavaScript engine is also included in your app so it can interpret your logic at run-time, which guarantees that the code you write once will run on any platform that your app ships to.

Third, React Native ships with Fabric. Fabric is a graphics rendering engine that has been built from the ground up. Where React stops caring what happens to a Component Tree after it has built one, Fabric takes over to make your app come to life on-screen. It first translates the Component Tree to a UI-centric version of that tree, named the Shadow Tree. This tree contains only the visual subset of elements from the Component Tree. It then calculates the sizes and positions of these elements on the screen and communicates the results of that calculation to the host environment that your app is running in by using that environment’s native APIs. The host environment then brings those elements to life on screen.

Fourth, React ships with Yoga, the layout engine that is used by Fabric to calculate the sizes and positions of elements in their layout. Yoga implements the Flexbox specification, bringing a singular UI-building standard to all supported platforms.

When your React Native app is spun up, all four of these pieces work together in an iterative pipeline to maintain a representation of your application and display it on screen. Here is a basic overview of that architecture.

On the left, we have our business logic and the React libraries. Metro has bundled them with our app. At run-time, Hermes interprets their instructions and transforms your business logic into an Element Tree. Next, Fabric’s render pipeline kicks in. During the render phase, Fabric takes your Element tree and reduces it to a Shadow Tree that consists of only visible components. Such visible components are called Host Components. In contrast, MyComponent is a so-called Composite Component. It’s user-created, and groups together Host Components, so it doesn’t correspond to anything on the screen itself and is omitted from the Shadow Tree.

After the render phase, the resulting Shadow Tree is committed. During this commit phase, Yoga is used to provide each node in the tree with layout information based on your component structure and styling choices.

Lastly, the mount phase translates the resultant tree to a native view by communicating with the host system. This pipeline then repeats, iterating every time an event leads to changes in the UI.

Now that you know a little about the React Native architecture, let’s see what implications these architectural choices have for us as we form a styling strategy.

Architectural Implications

React

Modern React components are written as functions that call each other using JSX syntax, passing along arguments that the UI relies upon. An important aspect of the arguments that are passed around is that they are particular to each component. Essentially, this means that every component that you write in React has its own unique API that accepts a specific input and produces a specific output. When you weave those components together, it’s easy to see what kind of maintenance overhead this can lead to as your code expands and transforms. Since JavaScript doesn’t provide compile-time type safety, any change you introduce to a component has the potential to silently cause runtime bugs. And as your code base expands with many new, unique APIs, you will notice your app become increasingly more challenging to maintain.

Yoga and Hermes

I’m sure you’ve heard of CSS. It has been adding flair and polish to the Web for close to thirty years. For the first twenty of those, that surface polish has belied what went on under the hood. Those long decades were spent hacking and tinkering together stopgap techniques, positioning and sizing elements in one browser only to break them in the next. This messy approach was the norm, until one day the Flexible Box Layout Module graced the Web.

Flexbox, as it is more commonly known, offered much needed reprieve from the inexact and patchy methods of the past. Not only did it unify browser behavior with a common standard, but it offered powerful methods to create flexible layouts and responsive designs with relative ease. It was so well-suited to modern needs that it was quickly adopted by various technologies outside of browsers. That brings us back to React Native.

React Native incorporates Flexbox by including the open-source layout engine called Yoga. The Flexbox standard, in turn, is based on CSS. The consequence is an architectural cascade that makes it so React Native must also support CSS. But since business logic in React Native is interpreted entirely by the Hermes JavaScript engine, the supported flavor of CSS must also be JavaScript. React Native solves this problem by accepting JavaScript objects that approximate CSS syntax. But these objects noticeably deviate from the version of CSS you may be familiar with. In addition to this eccentricity, the supported flavor of Flexbox has some quirks of its own.

Flexbox was made for the web, where it requires you to specify which HTML elements participate in the flex layout since browsers support different layout models. But React Native relies heavily on Flexbox layouts, so there is no need to specify whether something is a flex container. Instead, native elements participate in the flex layout by default. Additionally, the Flexbox specification mentions which default values apply to flex containers and flex items when no explicit choices are made by the implementer, but Yoga deviates from these defaults. 

For instance, in React Native, flex containers have a main-axis direction with the default value column instead of row, and flex items have a default flex-shrink value of 0 instead of 1. Additionally, Yoga doesn’t actually implement all of the Flexbox standard’s behaviors. Support for properties such as gap, row-gap and column-gap have only recently been added, while the min-content and max-content values are still unsupported. To add further confusion, the popular shorthand notation flex: <positive value> does work the same as on the web, implicitly changing flex-shrink from 0 to 1 in React Native. In contrast, the flex-shrink value remains unchanged in web layouts because, as I’ve mentioned, it already defaults to 1!

Dealing with such subtle nuances leads to maintenance overhead, so in our development strategy, we’re going to address how to deal with these subtleties.

Fabric

Lastly, we need to understand something about the render pipeline. In Hermes, the React library represents your UI as a tree of components. But not every component in that tree is shadowed in Fabric’s Shadow Tree, which means that not all components become visual. Only Host Components do. It’s important to understand this distinction. Host components correspond to something the host platform can show on your screen. That means you can make choices regarding their appearance and positioning. You do this using React Native’s version of CSS. But you won’t be able to style your user-defined Composite Components since they themselves don’t translate to anything on your screen. Rather, they return Host Components that do render to the screen.

Effective Styling in React Native

Now that you are familiar with these core principles, it’s time to form a strategy that deals with all of the described implications and empowers us to comfortably maintain our application. To save you some time, I won’t introduce all the alternative options. Instead, I’m going to skip right to my own recommendations. You can refer to the React and React Native documentation if you’d like to explore other alternatives.

Styling basics

Since a significant part of your time developing will be spent on styling, I recommend that you make it easy to find your styles and to tell where they are being applied. A common approach is to create a separate styles folder and fill it with files that contain styling. While this works, it still means you have to go browsing for the relevant styles when you need them. For that reason, I recommend relying on the principle of proximity instead.

The idea is that things that change together are placed together. As you may know, React as a framework combines structure, business logic and styling into components. But things can get messy when you group code into modules that have too many responsibilities. That’s why I recommend giving each component a folder by its own name, and creating a file for the component and another for the styling used by that component. You can add more files that relate to your component depending on your needs. Here is an example of what that might look like:

In addition to making things easy to find, this structure has the benefit that it allows you to group your relevant test files, storybook pages, markdown documentation and any other related files together under the same folder.

As for the actual method of styling, I recommend writing StyleSheet objects in your .style.ts files and importing them in your components. This approach has the simplicity of writing plain JavaScript objects, but with a few added benefits. These benefits include integration with official debugging tools, better error checking by linters and object immutability, which prevents unintended runtime changes to your exported style objects.

And there is yet another benefit to this approach. On the web, CSS is often written in Sass and transpiled to CSS. This enables a lot of features that enhance developer convenience. Using StyleSheet, your syntax resembles the groupings of styles that you place below selectors in CSS, while actually being plain JavaScript. This allows you to leverage JavaScript to unlock benefits similar to those that Sass provides.

Take, for instance, the following Sass that has a mixin with no arguments:

// example.scss

@mixin button {
 padding: 10px 20px;
 background-color: #000000;
}

.button {
@include button;
 color: #FFFFFF;
}

.button--red-text {
@include button;
 color: #FF0000;
}

Since mixins behave like functions, in React Native, you could achieve similar convenience like this:

// example.style.ts
import { StyleSheet } from 'react-native';

const button = {
 paddingVertical: 10,
 paddingHorizontal: 20,
 backgroundColor: '#000000',
};

export const styles = StyleSheet.create({
 button: {
   ...button,
   color: '#FFFFFF',
 },
 buttonRedText: {
   ...button,
   color: '#FF0000',
 }
});

This object destructuring allows us to include all the properties on a single line, much like an @include tag would. And if you wanted to use arguments with your mixin, it would only take you a few seconds to refactor button to a function call that returns an object instead:

const button = (color: string = '#FFFFFF') => {
 return {
   color,
   backgroundColor: '#000000',
   paddingVertical: 10,
   paddingHorizontal: 20,
 };
};

I recommend experimenting with the possibilities JavaScript offers to increase the maintainability of your styles depending on your needs. I think you will find you can do everything that Sass can and more with just as little syntax.

Now, the astute reader will have noticed the file extensions and some of the syntax I’ve used are typical of TypeScript files. As I’ve mentioned earlier, React projects are prone to introducing run-time bugs due to the many interdependent APIs. There used to be multiple popular approaches to solving this issue, but these days, TypeScript is the de-facto approach. I highly recommend using it.

Not only do you get convenience features such as type completion, but your styles benefit heavily from the combination of TypeScript and StyleSheet. After all, all your styling is done in JavaScript, allowing it to be type-checked at compile-time. And as it turns out, the StyleSheet.create() API comes equipped with type definitions that ensure that any style object we attempt to make actually corresponds to something that Host Components can accept as styling. Earlier, I mentioned that the React Native variant of CSS isn’t quite the same as on the web. With these type definitions, you don’t have to worry getting confused. TypeScript will correct your mistakes, and help you type to boot.

Let’s see what a possible implementation of a component looks like when we apply the advice I’ve given so far:

// Title.style.ts
import {basicTextMixin} from '<mixins folder>/text.ts';

// Type checks prevent us from adding values the fontWeight property can't accept
const TitleStyle = StyleSheet.create({
 titleText: {
   ...basicTextMixin(),
   fontWeight: '500',
 },
});
};

export default TitleStyle;


// Title.tsx

import {FunctionComponent} from 'react';
import {Text, View} from 'react-native';
import style from './Title.style';

interface Props {
 titleText: string;
}

const Title: FunctionComponent<Props> = ({titleText}) => {
 return (
   <View>
     <Text style={style.titleText}>{titleText}</Text>
     </View>
 );
};

export default Title;

TypeScript enforces compatibility between the styles that we’ve defined and the Text component that accepts them. Even ignoring compatibility with Host Components, simply passing an object into StyleSheet.create() causes type checks that ensure we can’t mismatch properties and values.

And the benefits don’t stop with Host Components. Imagine a scenario where you want to make Title’s styles adjustable. You could write something like this:

// Title.tsx

import {FunctionComponent} from 'react';
import {Text, View} from 'react-native';
import style from './Title.style';

interface Props {
 titleText: string;
 customStyles?: TextStyle;
}

const Title: FunctionComponent<Props> = ({titleText, customStyles = {}}) => {
 return (
   <View>
     <Text style={}>{titleText}</Text>
     </View>
 );
};

export default Title;

Title now accepts an extra optional prop called customStyles. This allows the caller to pass through extra styles. But it could lead to runtime bugs if the caller accidentally specified styles that Text is not compatible with. With TypeScript you can enforce that a compatible style prop is passed through at compile-time, so styles that pass through Composite Components are checked at the gate even before they reach their destination Host Component. Having type completion and three layers of type checks makes it very hard for your styles and other props to lead to run-time bugs.

And the best part is that any future breaking changes your team makes will immediately become obvious during development.

If you choose to use TypeScript, please note that React Native doesn’t use the TypeScript compiler during its compilation process. It only relies on Babel to transpile your TypeScript code to JavaScript. Babel, however, doesn’t care if your types make sense. It only cares that your code is written in valid syntax! So, while your IDE might provide you with type completion and alert you of type errors during development, React Native itself will not complain about mismatched types during compilation. I recommend that you use the TypeScript compiler with the noEmit flag separately as one of your quality gates to type-check your project. If you don’t have a CI/CD pipeline, you can run it as part of your bundling command to automatically check for type errors before your code gets bundled.

Flexbox

By now, our basic setup already provides convenience and mitigates a lot of maintenance overhead and bugs . But when using Flexbox, how can we deal with the different default values and the unintuitive shorthand notation flex: <positive value>?

The answer is simple: don’t use the shorthand. At best, it adds mental overhead when colleagues that aren’t well-versed in Flexbox try to understand what’s going on. At worst, it abstracts away a very nuanced change in the flex-shrink property that can lead to runtime bugs that are hard to find. Write your flex-basis, flex-grow and flex-shrink values explicitly when you want to change them.

As for the flex-direction that defaults to column, I think this should be easy enough for developers of any level to remember, so I don’t recommend burdening your team with any style rules there.

Before we move on from Flexbox, I should mention one exception to the rule that components participate in a flex layout by default.

Although <Text> components that are used as flex items behave exactly as other components would, they don’t act as flex containers. Imagine that you wanted to, say, write a paragraph with a clickable link in it. This paragraph needs to contain two <Text> nodes and a <Link> node in between. But if you were to add multiple nodes to a flex container, they would behave as flex items, spacing and aligning themselves according to the rules of Flexbox instead of flowing together and wrapping as a single piece of text. Instead of adding these elements to flex containers, you can nest multiple <Text> and <Link> components inside one another to get the neat paragraph of text you would expect.

That concludes the styling basics. If you’ve made it this far, congratulations! Our styling strategy is looking pretty solid at this point, so if you’re starting to feel overwhelmed, feel free to pause here and take these lessons with you to your next project. If you’re ready to learn more, check out part two of this article.
