Applying Polymorphism to a REST API using Spring Boot

In an object oriented programming language like Java, it is common to use inheritance. A feature of inheritance is that a class can take different forms (i.e. a class that extends another class). This phenomenon is called polymorphism. A powerful attribute of polymorphism in Java is the ability to use polymorphic parameters in methods; a method that takes a class as a parameter, can be called with an instance of a subclass of that class. This article explains how to apply this powerful mechanism to a REST API with Spring Boot. 
 

Data Transfer Objects
When implementing a REST API, it is common to use Data Transfer Objects (DTO's). DTO's are simple objects (e.g. listing 1) that only contain data that is necessary for exchanging information when interacting with an application. 

Listing 1:

public class VehicleDto {
    private Long id;
    private VehicleType vehicleType;
    private String brand;
    private String model;


    // ... getters and setters
}

Most of the time, DTO's are a representation of a complex domain model in the backend of an application. Listing 2 shows a simplified controller that can save the VehicleDto and can return all saved vehicles. To be able to map the DTO to the domain model and vice versa, the controller uses a mapper (VehicleMapper). By using this mapper, we make sure that the controller only receives and returns DTO's.
 

Listing 2:

@RestController
@RequestMapping("/vehicles")
public class VehicleController {
    private final VehicleService service;
    private final VehicleMapper mapper;


    // ... constructor


    @PostMapping
    public VehicleDto postVehicle(@RequestBody VehicleDto dto) {
        var vehicle = mapper.mapToVehicleEntity(dto);
        service.saveVehicle(vehicle);
        return mapper.mapToVehicleDto(vehicle);
    }


    @GetMapping
    public List<VehicleDto> getAllVehicles() {
        return service.getVehicles()
                .stream()
                .map(mapper::mapToVehicleDto)
                .collect(Collectors.toList());
    }
}

Polymorphic DTO's

When a domain model consists of multiple subclasses, it might be desirable to model your DTO's likewise. In our example, we make the VehicleDto abstract and introduce a couple of concrete implementations for different vehicle types (listing 3). Also, an abstract middle layer is being introduced: MotorizedVehicleDto. This layer contains fields that are applicable to motorized vehicles, which in its turn is extended by several implementations of specific motorized vehicles.   
 

Listing 3:

public abstract class VehicleDto {
    private Long id;
    private VehicleType vehicleType;
    private String brand;
    private String model;


    // ... getters and setters
}


public abstract class MotorizedVehicleDto extends VehicleDto {
    private String licensePlate;
    private int horsePower;
    private FuelType fuelType;


    // ... getters and setters
}


public class CarDto extends MotorizedVehicleDto {
    private int numberOfDoors;
    private BodyStyle bodyStyle;


    // ... getters and setters
}


public class BusDto extends MotorizedVehicleDto {
    private BusType busType;
    private int litersLuggageCapacity;


    // ... getters and setters
}

When all the different implementations of the VehicleDto are to be handled by the same endpoints which are mentioned in listing 2, we have a candidate to apply polymorphism to a REST API. 

Serialization and Deserialization 
A topic we come across when applying polymorphism to REST is serialization. By serialization we mean in this context: converting a Java object into a form suitable for transmission (e.g. text). Deserialization is the opposite: creating a Java object from a serialized form. In the examples in this article, we communicate with the REST API via JSON. When referring to serialization in the upcoming examples, we mean converting a DTO to JSON; deserialization means converting JSON to a DTO.

Jackson
In a Spring Boot application, Jackson is the default library for mapping JSON. This means that Jackson handles serialization and deserialization when communicating with the application via REST. In most cases, Jackson is able to map a DTO without supplying specific configuration. For situations where specific behavior is needed in this process, Jackson offers several annotations to configure this. Our use case with the polymorphic DTO's from Listing 3 is an example of this.

Polymorphism and Jackson
Because of the object oriented nature of Java, you can define a method that takes a superclass as a parameter and call it with a subclass. So, in Java it is possible to create a method that takes a VehicleDto and call that method with a CarDto; a CarDto is a VehicleDto after all (see listing 3). Wouldn’t it make sense that doing an HTTP POST with a CarDto JSON (listing 4), this JSON deserializes as a CarDto which can be handled by our controller then? Not automatically!
 

Listing 4:

{
"vehicleType": "CAR",
"brand": "Toyota",
"model": "C-HR",
"licensePlate": "07-88-RE",
"horsePower": 180,
"fuelType": "HYBRID",
"numberOfDoors": 4,
"bodyStyle": "SUV"
}

Without adding additional configuration, Jackson doesn't interpret the subclasses of VehicleDto because it isn't aware that VehicleDto has subclasses; Jackson is only aware of the VehicleDto class since the controller from listing 2 only has methods that return or receive a VehicleDto. Doing a HTTP POST to the /vehicles endpoint with a CarDto, results in the deserialization of a VehicleDto while all CarDto specific attributes are being ignored. Also, in our example the Jackson library throws an exception as shown in listing 5, since an abstract class cannot be instantiated.

Listing 5:
 

com.fasterxml.jackson.databind.exc.InvalidDefinitionException: Cannot construct instance of `nl.kooi.vehicle.api.dto.VehicleDto` (no Creators, like default constructor, exist): abstract types either need to be mapped to concrete types, have custom deserializer, or contain additional type information

Since the VehicleDto is an abstract class containing fields that are shared amongst different vehicle types, it can only be instantiated with a concrete implementation. This would mean that every concrete implementation of VehicleDto needs its own endpoint(s). If you have a use case where you would like the same set of endpoints to be able to handle each (future) implementation of VehicleDto, this is a no go.

 The exception in listing 5 already gives us some hints on how to tackle this:

  • Using concrete types;
  • Having a custom deserializer;
  • Adding additional type information.

We will elaborate on adding additional type information, since this is a simple and non verbose form of configuring polymorphism in Jackson.

Adding additional type information
When providing Jackson with additional type information, there are two Jackson specific annotations you should be aware of. Those are @JsonTypeInfo and @JsonSubTypes. The first one describes how type information can be obtained; the second one describes which subtypes we acknowledge. Logically, we put these annotations on top of the super class (in our example the annotations are put on VehicleDto).

Since VehicleDto contains an enum field named vehicleType (which can be either BUS or CAR), this would be a good candidate to distinguish between the different subtypes. The implementation of this is in Listing 6.

Listing 6:
 

@JsonTypeInfo(
        include = JsonTypeInfo.As.EXISTING_PROPERTY,
        property = "vehicleType",
        use = JsonTypeInfo.Id.NAME,
        visible = true
)
@JsonSubTypes({
        @JsonSubTypes.Type(value = BusDto.class, name = "BUS"),
        @JsonSubTypes.Type(value = CarDto.class, name = "CAR")
})
public abstract class VehicleDto {
    private Long id;
    private VehicleType vehicleType;
    private String brand;
    private String model;


    // ... getters and setters
}

The @JsonTypeInfo annotation indicates that an existing field (vehicleType) is used to distinguish between different subtypes. By adding use = JsonTypeInfo.Id.NAME, Jackson will distinguish subtypes by the value of the vehicleType field. The visible = true configuration is added to indicate that the corresponding field needs to be serialized.

The @JsonSubTypes annotation indicates which subtypes are acknowledged (BusDto and CarDto), and what value the field from the @JsonTypeInfo description (vehicleType) has in case of the given subtype.

Consuming polymorphic DTO's

What if we would like to introduce a new vehicle type like the one in listing 7? Now this is where the power of this mechanism comes in place; adding a new vehicle type is nothing more than introducing the new DTO, adding a new value to the VehicleType enum and defining the new type in the @JsonSubTypes annotation.  
 

Listing 7:

public class BoatDto extends VehicleDto {
    private PropulsionType propulsionType;
    private int lengthMeters;
    private int draftMeters;


    // ... getters and setters
}


Listing 8:

@JsonTypeInfo(
        include = JsonTypeInfo.As.EXISTING_PROPERTY,
        property = "vehicleType",
        use = JsonTypeInfo.Id.NAME,
        visible = true
)
@JsonSubTypes({
        @JsonSubTypes.Type(value = BusDto.class, name = "BUS"),
        @JsonSubTypes.Type(value = CarDto.class, name = "CAR"),
        @JsonSubTypes.Type(value = BoatDto.class, name = "BOAT")
})
public abstract class VehicleDto {…}

That's it! Notice that we didn't change our controller from listing 2 to be able to handle the new DTO. After all, the controller isn't aware of the serialization process since this is handled by Jackson before and after interacting with the methods in the controller.


Other ways to distinguish between types using @JsonTypeInfo
In the previous example, the type of the DTO was determined by a field that is part of the VehicleDto: vehicleType. This was configured by adding include = JsonTypeInfo.As.EXISTING_PROPERTY to the @JsonTypeInfo annotation. The @JsonTypeInfo annotation can also be configured differently. 

When the include-property is omitted, Jackson will use the default way of determining the type: JsonTypeInfo.As.PROPERTY. The difference with EXISTING_PROPERTY is that it now uses a field that is added for serialization purposes only. This field is considered as meta-information and is not part of the DTO. The field name still needs to be defined in the property field of the annotation. Listing 9 shows how this configuration will look like. In this example, the include-property is explicitly included for illustration purposes. Also, the @JsonSubTypes annotation is provided with new names ("BusDto" and "CarDto"). Other than changing the configuration in these two annotations, the content of VehicleDto isn’t changed.
 

Listing 9:

@JsonTypeInfo(use = JsonTypeInfo.Id.NAME,
        include = JsonTypeInfo.As.PROPERTY,
        property = "type",
        visible = true)
@JsonSubTypes({
        @JsonSubTypes.Type(value = BusDto.class, name = "BusDto"),
        @JsonSubTypes.Type(value = CarDto.class, name = "CarDto")
})
public abstract class VehicleDto {…}

Image 3 shows how a request to the POST-endpoint with this new configuration will look like. The JSON that is being used to do the HTTP POST request (shown in the top part of image 3), is now extended with a "type" field to indicate that this JSON represents a BusDto. In the response (the lower JSON in image 3) this field is also being serialized so that this meta-information can be used by a calling party (i.e. a frontend application).
 

Image 3:

Jackson also facilitates other configurations in the @JsonTypeInfo annotation to distinguish between subtypes; these are not discussed in this article, but please note that the ways of handling subtypes with Jackson are not limited to the two ways shown in this article.

Conclusion
Jackson provides a number of ways to (de)serialize subclasses. By adding extra configuration to a superclass, you can have the same set of endpoints in your REST API deal with different subtypes of a DTO. This can be done without changing the contract of your API. On the one hand, this ensures that your API is easily extensible. On the other hand, it does make it necessary to provide good documentation about the API to properly inform clients about which fields are needed for the specific situation. It is also handy to know that CodeGen tools which are used to generate APIs and API documentation (such as Swagger CodeGen) often provide support for setting up and documenting subtypes.

When the principles of object oriented programming are applied consistently in all layers of a backend application, it will result in a well-maintainable and extensible codebase. Working in such a codebase will provide a lot of fun.
