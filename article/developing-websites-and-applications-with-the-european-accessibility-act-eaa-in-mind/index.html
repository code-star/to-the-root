Developing websites and applications with The European Accessibility Act (EAA) in mind

by
Dennis Rosema

On June 28, 2025, the European Accessibility Act, also known as EAA, will be applied. This new accessibility law aims to equal access to digital products and services in Europe to all people, particularly people with disabilities. In this article I will give you some tips, how to make your application accessible for your end-users.

WCAG

The starting point is always the WCAG, the Web Content Accessibility Guidelines. These guidelines are the basics of an accessible website or application. A list of the guidelines can be found on the w3 website. The WCAG has 4 main principles you need to apply to for an accessible application:

  • Perceivable: Users must be able to understand the information being presented.
  • Operable: User interface components and navigation must be operable.
  • Understandable: Content should be understandable by the users 
  •  Robust: Content must be robust enough that it can be interpreted reliably by a wide variety of user agents, including assistive technologies.

Let’s see how we can apply these principles in our applications.

Semantic HTML

Semantic HTML is crucial for accessibility because it provides meaningful structure and context to web content, which helps assistive technologies (such as screen readers) and search engines understand and interpret the content more effectively. The list of good semantic HTML elements keeps growing and these semantic HTML elements, like button, dialog, nav, form etc. are very well accessible

This should always be your first concern. A good starting point to get information about Semantic HTML is the Mozilla HTML page. 

If you want to test semantic HTML, you can use the W3C Markup Validator or use the Lighthouse option in your chrome inspector.

Bad practice of using semantic HTML:

<body>
  <div>
      <div>Navigation</div>
  </div>
  <div>
      <div>
          <div>
              <strong>This is a heading</strong><br/>
              This is the main content of the website.
              <div onclick="clickme()">This is a button</div>
          </div>
      </div>
      <div>Extra information.</aside>
  </div>
  <div>Page footer content</div>
</body>

This code is bad for accessibility because it uses generic <div> elements instead of semantic HTML elements like <header>, <nav>, <main>, <article>, <aside>, and <footer>. Semantic elements provide better context and meaning to the content, making it easier for screen readers and other assistive technologies to understand the structure of the page.

Good practice of using semantic HTML:

<body>
  <header>
      <nav>Navigation</nav>
  </header>
  <section>
      <main>
          <article>
              <h1>This is a heading</h1>
              <p>
                  This is the main content of the website.
              </p>
              <button onclick="clickme()">This is a button</button>
          </article>
      </main>
      <aside>Extra information.</aside>
  </section>
  <footer>Page footer content</footer>
</body>

Principle: Understandable / Robust

Navigation

Clear and accessible navigation is essential for helping all users, including those with disabilities, to easily find and access the content they need. To achieve this, it is important that you use a consistent layout and standard positioning for navigation elements across all pages. This consistency helps your users predict and locate navigation links more easily.

For links, you should use a descriptive text that clearly indicates the destination or action, and implement accessible menus enhanced with ARIA (Accessible Rich Internet Applications) roles and properties to provide additional context for assistive technologies.

You can also use breadcrumbs to offer a clear path of the user's location within the site hierarchy, aiding in navigation back to previous sections. Make sure that navigation elements are responsive and usable on any device.

Bad practice of implementing navigation:

<body>
  <div>
      <ul>
          <li><a href="#home">Home</a></li>
          <li><a href="#about">About</a></li>
          <li><a href="#services">Services</a></li>
          <li><a href="#contact">Contact</a></li>
      </ul>
  </div>
</body>

The navigation above is bad for accessibility because it lacks proper semantic HTML elements like <nav> for navigation. Additionally, there are no ARIA roles or attributes to enhance the navigation experience for users with disabiliti

Good practice of implementing navigation:

<body>
  <nav aria-labelledby="main-navigation">
      <h2 id="main-navigation" class="visually-hidden">Main Navigation</h2>
      <ul role="menubar">
          <li role="none"><a href="#home" aria-label="Home Page" title="Home Page" role="menuitem">Home</a></li>
          <li role="none"><a href="#about" aria-label="About Us" title="About Us" role="menuitem">About</a></li>
          <li role="none"><a href="#services" aria-label="Our Services" title="Our Services" role="menuitem">Services</a></li>
          <li role="none"><a href="#contact" aria-label="Contact Us" title="Contact Us" role="menuitem">Contact</a></li>
      </ul>
  </nav>
</body>

Principle: Operable

Text alternatives

When you use images, provide text alternatives by using the alt attribute to offer descriptive text, ensuring that visually impaired users can understand the content. Additionally, utilize ARIA attributes such as aria-label, aria-labelledby, and aria-describedby to give additional context for interactive elements, making them more comprehensible for users relying on assistive technologies.

Bad practice of using a normal image:

<body>
  <img src="image.jpg">
</body>

The image in the above example is missing the alt attribute, which provides alternative text for screen readers, which is essential for visually impaired users to understand the content of the image when the image is meaningful.

Good practice of using a normal image:

<body>
  <img src="image.jpg" alt="Description of the image">
</body>

Bad practice of using a decorative image:

<body>
  <img src="decorative-image.jpg" alt="Description of the image">
</body>

To properly mark an image as decorative, you should use an empty alt attribute (alt=""). This tells screen readers to ignore the image.

Good practice of using a decorative image:

<body>
  <img src="decorative-image.jpg" alt="">
</body>

Principle: Perceivable

Keyboard accessibility

For keyboard users, make sure that all interactive elements such as links, buttons, and form controls are focusable and can be navigated using the keyboard. Maintain a logical tab order to provide a smooth navigation experience for keyboard users.

On the top of your page, you can include a skip links menu, to enable users to bypass repetitive content and navigate directly to the main content, enhancing the overall accessibility of your web app or site.

Bad practice of implementing keyboard accessibility:

<body>
  <div onclick="navigateToPage()">Clickable link</div>
  <div tabindex="0">Clickable div</div>
</body>

This code is bad for accessibility because it uses a div element with an onclick event, which is not keyboard accessible and does not provide semantic meaning. Additionally, the tabindex="0" on a div makes it focusable but does not convey its purpose or behavior to screen readers. You should use a link or button instead

Good practice of implementing keyboard accessibility:

<body>
  <a href="#">Clickable link</a>
  <button>Clickable button</button>
</body>

Principle: Operable

Color contrast

To have sufficient color contrast, you must check that text and interactive elements have a contrast ratio of at least 4.5:1 against their background for normal text and 3:1 for large text. Avoid relying solely on color to convey information by using text labels, patterns, or icons to ensure that content is accessible to users with color blindness. There are multiple nice plugins, like WCAG Color contrast checker, to check if you have sufficient contrast.

Principle: Perceivable

Forms

When you want to create accessible forms, make sure that all form controls have associated labels using the <label> element or aria-label to clearly identify their purpose. Also provide clear and descriptive error messages and instructions for form validation to guide users in correcting any mistakes.

Bad practice for accessible forms:

<body>
  <form>
      <div>
          <label>Name</label>
          <input type="text">
      </div>
      <div>
          <label>Email</label>
          <input type="email">
      </div>
      <div>
          <button>Submit</button>
      </div>
  </form>
</body>

The above form lacks accessible labels for screen readers because the <label> elements are not associated with their corresponding <input> elements using the for attribute. Also the button type is missing, if you want to submit a form you should use type=”submit

Good practice for accessible forms:

<body>
  <form>
      <div>
          <label for="name">Name</label>
          <input type="text" id="name" name="name">
      </div>
      <div>
          <label for="email">Email</label>
          <input type="email" id="email" name="email">
      </div>
      <div>
          <button type="submit">Submit</button>
      </div>
  </form>
</body>

Principle: Perceivable, Operable, Understandable, Robust

Audio & video

Another good practice for accessibility is to provide captions for videos to make the audio content accessible to users who are deaf or hard of hearing. Also, offer transcripts for audio content, allowing users to read the information if they cannot listen to it.

Bad practice using audio:

<body>
  <audio src="audio.mp3"></audio>
</body>

The above audio element is missing the audio controls. Also there is no fallback when the file can’t be played for some reason

Good practice using audio:

<body>
  <audio controls>
      <source src="audio.mp3" type="audio/mp3" />
      <source src="audio.ogg" type="audio/ogg" />
      <p>
        Your browser doesn't support HTML audio. Here is a
        <a href="audio.mp3">link to the audio</a> instead.
      </p>
  </audio>
</body>

For videos, you can include audio transcripts that narrate important visual details for users who are blind or have low vision. By incorporating these practices, you provide accessible multimedia content to a wider audience, ensuring that all users can fully engage with and understand the media on your web app or site.

Bad practice using video:

<body>
  <video src="video.mp4"></video>
</body>

The above video is also missing the controls property. Next to that the track property to provide transcriptions is missing. 

Good practice using video:

<body>
  <video controls>
      <source src="video.mp4" type="video/mp4" />
      <source src="video.webm" type="video/webm" />
      <track kind="subtitles" src="subtitles_en.vtt" srclang="en" />
  </video>
</body>

Principle: Perceivable

Readable text and zooming

Readability and zooming are very important to make your content accessible as well. For readable text and support for zooming, you should use a font size of at least 16px to enhance readability for all users. Maintain appropriate line height, typically 1.5 times the font size, to improve text legibility and reduce eye strain.

Make sure that your web application or site allows users to resize text up to 200% without loss of content or functionality, accommodating users with visual impairments. By doing this, you should avoid using fixed units for text sizes and instead use relative units like em or % to allow for better scalability. If you follow these practices, you create a more accessible and user-friendly experience for individuals who rely on larger text or need to zoom in to read content comfortably.

Principle: Perceivable

Testing your application

It is very easy to test your site or application with screen readers such as NVDA, JAWS, or VoiceOver to verify that content is accessible to visually impaired users. When I’m testing a website or application, I always do a test with only the keyboard to confirm that all interactive elements are accessible and navigable, ensuring a seamless experience for users who rely on keyboard navigation.

Conclusion

Thank you for reading my article, I hope it will inspire and help you build better accessible websites and applications. If you have any questions or feedback, please leave it in the comments section.
